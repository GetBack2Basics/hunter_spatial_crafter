Why I built this

For me, this is a conservation-minded project: not about saying no to development, but about helping identify where development can create the most value with the least harm. Siting decisions for national AI infrastructure should be transparent, constructive, and grounded in auditable spatial evidence.

AI data centers are exceptionally resource-intensive. They require heavy high-voltage grid transmission (≥132kV), tens of megalitres of cooling water, extensive contiguous flat land, and network connectivity—while creating potential acoustic, thermal, and environmental pressures on surrounding communities and ecosystems. I wanted to build a spatial engine that makes those tradeoffs visible instead of hiding them behind a single arbitrary score.

Why I used Wherobots

I wanted a platform that could handle national spatial scale without forcing me into slow, fragile desktop GIS workflows or complex infrastructure management.

This project queried 15.91 million authoritative geometries across 16 national and state/territory spatial datasets. At the regional modeling scale, our underlying NSW analysis stack ingested 1,751,315 geometries across 8 cloud spatial tables, evaluating 4.92 million spatial join combinations. Using cloud-native GeoParquet inside Wherobots Havasu (Spatial Iceberg) tables, the storage footprint was compressed from ~2.9 GB raw equivalent down to ~430.7 MB—an 85.2% storage reduction.

Verified Runtime Breakdown:
  • 2.4 Seconds: Wherobots Cloud Spatial SQL query execution for complex distributed joins and net developable area overlays across 1.75M+ geometries.
  • 18.4s ➔ 3.2s: Scan time acceleration across 15.91M national geometries using Hilbert space-filling curve partitioning.
  • 200.6 Seconds: Cold, end-to-end multi-table batch ETL pipeline execution (uncached ingestion, GDA2020 CRS reprojection, geometry topology validation via ST_MakeValid, and Iceberg table writing).
  • < 1 Millisecond: Client-side What-If sandbox recalculation in the browser with zero server round-trips.

What I was trying to learn

I wanted to understand how far I could push a cloud spatial workflow while still producing something that non-technical stakeholders, planners, and community members could directly interrogate. The answer was to combine Wherobots Cloud (Apache Sedona) for heavy distributed computation with a portable, self-contained "Map in a Box" HTML report for presentation.

The report (runner/national_suitability_report.html, hosted live at national-suitability-report.vercel.app) is the public-facing evidence layer. It includes an interactive continental map with live Geoscience Australia transmission lines, a ranked candidate leaderboard, multi-state benchmarking tables, and a real-time What-If simulation sandbox.

How the workflow works

The siting pipeline follows six structured stages:

  1. Ingest Authoritative Layers: Harvest spatial datasets from live government WFS/REST portals and national registers into cloud object storage.
  2. Apply Exclusions & Setbacks: Deduct 30m riparian corridors, 20m high-pressure gas/water pipeline easements, high-value biodiversity zones, slope >5%, and tailings dam hazards.
  3. Calculate Network Distances: Compute topological winding distances (1.32x factor) to ≥132kV transmission substations and wastewater treatment outfalls.
  4. Evaluate Sensitive Receptors: Apply a continuous sigmoidal buffer penalty around schools, hospitals, and residential meshblocks.
  5. Benchmark Against Regional Baselines: Compare candidates against Simulated Baselines across interstate transition hubs (Latrobe Valley, Collie, Gladstone).
  6. Publish Zero-Dependency Report: Compile all spatial layers, audits, and metadata into a standalone interactive HTML document.

The 4-Factor Multi-Criteria Scoring Model

The current production engine evaluates candidate suitability using four weighted factors:

Suitability = 0.40 · S_power + 0.25 · S_sensitive + 0.20 · S_water + 0.15 · S_size
  • Power Grid Proximity ($S_{\text{power}}$, 40%): Proximity to ≥132kV transmission substations. Full points between 100m and 500m; linear decay to 0.0 at 5km; 0.7 penalty under 100m for EMF safety and acoustic isolation.
  • Sensitive Receptor Buffer ($S_{\text{sensitive}}$, 25%): Evaluated using a continuous sigmoidal decay function around a 500m compliance threshold:
    S_sensitive(d) = 1 / (1 + e^(-0.01 · (d - 500)))
    Hard exclusion under 300m ($S=0.0$), acoustic barrier buffer penalty between 300m–500m ($S=0.10–0.50$), compliant zone 500m–1.5km ($S=0.50–1.0$), optimal workforce balance 1.5km–5km ($S=1.0$), and linear commute decay beyond 5km.
  • Recycled Water Proximity ($S_{\text{water}}$, 20%): Distance to wastewater treatment plants (WWTP) for sustainable evaporative cooling, decaying linearly from 1.0 at ≤1km to 0.0 at ≥10km.
  • Developable Parcel Size ($S_{\text{size}}$, 15%): Contiguous flat buildable land. Parcels ≥15 ha receive 1.0; parcels <3 ha receive a baseline of 0.1, with linear interpolation between.

The Spatial SQL underneath

With Apache Sedona running on Wherobots Cloud, multi-layer spatial operations execute via concise, standardized Spatial SQL.

1. Net Developable Area Mask (Topological Union & Difference)

Unioning riparian, pipeline, and biodiversity buffers and subtracting them from the gross masterplan sub-precinct boundary:

SELECT 
  p.precinct_key,
  ST_Difference(
    p.geom, 
    ST_Union_Aggr(c.geom)
  ) AS net_developable_geom,
  ST_Area(ST_Difference(p.geom, ST_Union_Aggr(c.geom))) / 10000.0 AS net_developable_ha
FROM org_catalog.fgsdb.macquarie_precinct_boundary p
LEFT JOIN org_catalog.fgsdb.macquarie_constraints_stack c
  ON ST_Intersects(p.geom, c.geom)
GROUP BY p.precinct_key, p.geom;

2. Nearest Infrastructure Distance Joins

Calculating geodesic distances from industrial candidate parcels to high-voltage transmission substations and wastewater treatment outfalls:

SELECT 
  mb.mb_code21,
  MIN(ST_Distance(
    mb.geom, 
    ST_Transform(sub.geometry, 'EPSG:4326', 'EPSG:7856')
  )) / 1000.0 AS dist_to_substation_km,
  MIN(ST_Distance(
    mb.geom, 
    ST_Transform(wwtp.geometry, 'EPSG:4326', 'EPSG:7856')
  )) / 1000.0 AS dist_to_wwtp_km
FROM org_catalog.fgsdb.abs_industrial_meshblocks mb
CROSS JOIN org_catalog.fgsdb.national_electricity_grid sub
CROSS JOIN org_catalog.fgsdb.national_water_hydrography wwtp
GROUP BY mb.mb_code21;

Benchmarking and speed mechanics

The Four Pillars of Wherobots Query Performance

  1. Zero-Scan Metadata Envelope Pruning: Havasu embeds 2D bounding box envelopes ([minx, miny, maxx, maxy]) directly inside Iceberg AVRO manifest files. Queries with predicates like ST_Intersects prune >95% of irrelevant Parquet files at the metadata layer before any raw disk bytes are read.
  2. Hilbert Curve Spatial Clustering: Geometries are spatially sorted using 2D Hilbert space-filling curves during ingestion. Geographically adjacent polygons and vectors land in identical Parquet row groups, eliminating random disk I/O seek overhead.
  3. Vectorized Memory Execution: Apache Sedona operates directly on columnar GeoParquet WKB geometry buffers, avoiding serialization overhead between Python, Java/Scala Spark JVMs, and native C++ spatial drivers.
  4. Parallel Distributed Spatial Joins: Quad-tree and R-tree spatial indexes partition the national query space across worker nodes, converting expensive $O(N \times M)$ cross-joins into efficient $O(N \log M)$ parallel bucket joins.
Important Note on Regional Baselines: Interstate comparison hubs (Simulated Baselines: Latrobe Valley in VIC, Collie in WA, Gladstone in QLD) represent modeled regional baselines. While detailed micro-siting setbacks (riparian, pipeline easements, DEM slope) are fully measured in the NSW Hunter precinct, national baselines serve as an optimistic upper-bound benchmark to contextualize opportunities across the National Electricity Market (NEM).

How the what-if sandbox runs with no server

The simulation sandbox runs entirely in the browser: zero server calls, zero network latency, and zero ongoing cloud API charges during an interactive slider session.

The heavy spatial work—topological winding distances, buffer overlaps, elevation slope drops, thermodynamic decay rates—is computed at build time on Wherobots Cloud and embedded in the report's JSON payload. Moving a weight slider normalizes values so weights sum to 1.0 and recalculates composite suitability in JavaScript in under a millisecond.

Toggling the Tailings Storage Facility (TSF) safety switch swaps pad areas between the declared and de-declared cases (+15.2 ha unlocked) and updates map polygons and audit cards instantly without refetching any GeoJSON.

Engineering efficiencies: reducing compute spend through incremental spatial processing

While our total cloud batch compute spend across dozens of iterative development, benchmark, and QA runs was already modest at ~$36 AUD (US$24.13), analyzing the execution profile reveals how production spatial pipelines can reduce costs even further by eliminating redundant computation.

1. Decoupling Heavy Geometry Joins from Lightweight Multi-Criteria Scoring

Spatial siting pipelines consist of distinct computational tiers with vastly different resource requirements:

  • Heavy Geometric Tier (Compute-Intensive): Ingesting raw vector feeds, reprojecting to GDA2020 (EPSG:7856), repairing invalid topologies (ST_MakeValid), constructing 30m/20m spatial buffers, and computing ST_Difference developable overlays across millions of polygons.
  • Lightweight Vector Scoring Tier (Compute-Light): Evaluating mathematical decay curves ($S_{\text{power}}$, $S_{\text{sensitive}}$, $S_{\text{water}}$) and weighted composite scores against precomputed distance attributes.

By structuring the pipeline as a directed acyclic graph (DAG) with intermediate materialized GeoParquet stages, tuning a scoring weight or modifying the sigmoidal acoustic threshold ($d_0$) never triggers a re-run of the heavy geometric spatial joins. Only the downstream mathematical matrix recalculates.

2. Source-Level Data Fingerprinting & Snapshot Memoization

Authoritative baseline layers (e.g. 275k rail vectors, 241k power grid features, or 15.4M cadastral parcels) change infrequently. Implementing cryptographic content hashing (ETags, GeoParquet file hashes, and Iceberg snapshot manifest IDs) ensures that untouched spatial tables are bypassed during batch execution, reading directly from cached Havasu storage partitions.

3. Delta Partition Processing (Iceberg Time-Travel)

When state planning portals publish quarterly cadastral updates, leveraging Apache Iceberg's ACID snapshot metadata allows Sedona to isolate and process only modified parcel geometries (ST_Changes) rather than executing full continental scans.

4. Zero-Cost Client Compute Offloading

By compiling precomputed distance topologies into the standalone HTML report and offloading real-time multi-criteria exploration to in-browser JavaScript and DuckDB-WASM, millions of interactive public scenario evaluations occur at $0.00 cloud compute cost.

Efficiency Impact: Applying strict target-level memoization and delta processing reduces continuous CI/CD pipeline costs from ~$36 AUD down to < $5 AUD, enabling rapid iterative spatial engineering at a fraction of standard cloud GIS operational overhead. What's next (Author Roadmap)

The following section outlines the author's planned technical roadmap and open-source integration, not currently shipped Wherobots platform features.

1. Sensitive Receptor Scoring Expansion

Continuing the integration of live authoritative registers (ACARA, NHSD, and OpenStreetMap) across all states to evaluate acoustic, thermal, and visual setbacks against schools, hospitals, and residential zones.

2. Grid & Water Policy Alignment

Following recent National Cabinet discussions on AI data center power demand and regional grid security, the framework will map candidate sites against Renewable Energy Zones (REZs), 24/7 clean energy firming storage, and coal-fired station transmission reuse, restricting cooling strictly to recycled water loops.

3. Open-Source GeoLibre AI Platform Integration

To enable the public to query these models using natural language ("Ask AI"), the repository will connect to an open-source opengeos/GeoLibre deployment hosted serverless on Google Cloud Platform (GCP).

Zero-Duplication Cloud Architecture: Wherobots writes processed suitability layers directly to cloud storage (S3/GCS) as GeoParquet and PMTiles. GeoLibre's in-browser DuckDB-WASM engine executes SQL by fetching only required byte ranges via HTTP range requests—eliminating dataset duplication, server-side data copying, and large client downloads.

It gave me a clean path from raw authoritative geodata to a polished, reviewable spatial document—one that can be opened by a stakeholder, audited by a technical reviewer, and debated constructively in public.

For a personal project, that was the goal: learn the platform, test it at real national scale, create something useful, and contribute to the broader discussion about responsible AI infrastructure.
